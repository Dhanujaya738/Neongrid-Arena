Part A — The big picture

A1. What we built, in one paragraph

NeonGrid is an online Ultimate Tic-Tac-Toe game. Players open a web page (on a laptop or phone), choose a name and play each other or an AI bot. Behind the page is our own Java server, written with no frameworks. It accepts every connection, speaks several network protocols, keeps the official game state, checks every move, and sends the new board to everyone in the room. A second page, the Network Control Room, lets the evaluator look inside the server while it runs.

A2. Why there is a separate Control Room

Early versions put the technical panels (packet inspector, security lab, connection info) inside the game. That made the game confusing: a normal player could not tell what the game was. So we separated the two, which is also how real systems are built.

ReasonExplanation
1. Good user experienceA player wants to play, not read HMAC values. The game page contains only game things: board, players, chat, results. This is the separation of concerns principle: each screen has one job.
2. Security (authorization)The Control Room shows sensitive data: every player's IP address and port, reverse-DNS host names, server internals, and an attack tool. If that were in the game, any player could see other people's IPs or attack the server. So it is protected by an admin password, and the server refuses admin commands from anyone who hasn't logged in (FORBIDDEN). This is least privilege from the Secure NP lecture.
3. Networking is invisibleYou cannot see NIO, threads, UDP or HMAC while playing. The evaluator needs proof that our concepts are really working. The Control Room makes them visible: "300 sockets on 10 threads", every packet with its MAC, every blocked attack, every AI job and which thread ran it.
4. It mirrors the real worldReal online games have a player app and, separately, an operations dashboard (like Grafana or Wireshark) that only engineers can open. Our project follows the same pattern.
5. No effect on playersThe Control Room is just another (admin) client. Packet capture only runs while an admin is logged in (metrics.captureOn), so normal play is never slowed down.

How to reach it: click the small purple antenna icon at the top right of the game (it opens in a new tab), or go to http://localhost:8080/control. Password: arena-admin. Change it with ./scripts/run-server.ps1 --admin-pass NewPass.

Member A — Java NIO: one thread, every socket

Lecture: Network Programming with NIO (channels, buffers, selectors, non-blocking I/O). Your files: server/Reactor.java, server/Connection.java (reading and writing parts), client/BotSwarm.java.

A.1 The concept in simple words

With traditional (blocking) I/O, a server needs one thread per client, because read() stops the thread until data arrives. 1000 players means 1000 threads, each using memory and causing context switches. With NIO, channels are put into non-blocking mode and registered with a Selector. One thread asks the selector "which channels are ready?" and only handles those. Nobody waits, so one thread can serve thousands of sockets.

Think of a waiter: the blocking server hires one waiter per table who stands there waiting. The NIO server has one waiter who walks around and only serves tables that have raised their hand.

A.2 How it was built

Step 1: open non-blocking channels and register them (Reactor constructor)

selector = Selector.open();
serverChannel = ServerSocketChannel.open();
serverChannel.configureBlocking(false);                      // non-blocking
serverChannel.bind(new InetSocketAddress(config.tcpPort), 256);
serverChannel.register(selector, SelectionKey.OP_ACCEPT);       // "tell me when a client connects"
udpChannel = DatagramChannel.open(); udpChannel.configureBlocking(false);
udpChannel.register(selector, SelectionKey.OP_READ);            // UDP on the SAME selector (Member D)

Step 2: the event loop (Reactor.run())

while (running) {
    int ready = selector.select(wait);                // sleep until something is ready (or a timer is due)
    Iterator<SelectionKey> it = selector.selectedKeys().iterator();
    while (it.hasNext()) { SelectionKey key = it.next(); it.remove(); dispatch(key); }
    runTasks();     // jobs posted by other threads
    completeJobs(); // finished worker Futures (Member C)
    runTimers();    // turn clocks, reconnect grace periods, 1-second stats tick
}

dispatch() looks at the key: acceptable → accept() new clients; the UDP channel → Discovery.onReadable(); otherwise the key's attachment is that client's Connection, so it calls onReadable() / onWritable().

Step 3: accepting clients (Reactor.accept())

A non-blocking accept() returns null when nobody is waiting, so we loop until null. Each new SocketChannel is set non-blocking, registered for OP_READ, and gets a Connection object attached to its key.

Step 4: reading with ByteBuffer (Connection.onReadable()), the most important part

int n = ch.read(in);                // copy whatever bytes arrived into the buffer (write mode)
if (n < 0) { close(...); return; }   // -1 = the client closed the connection (TCP FIN)
in.flip();                          // switch to read mode: limit = position, position = 0
decode();                           // take out every COMPLETE frame
in.compact();                       // move unfinished bytes to the front, back to write mode

TCP is a stream: one read may contain half a message or three messages. decode() first peeks at the header without moving the position (in.getInt(in.position())). If the whole frame hasn't arrived yet it stops, and compact() keeps those bytes so the next read appends to them. This is exactly the lecture's "LOGIN Amal\nPASS" example. If a frame is bigger than the buffer, growBuffer() doubles it (up to 256 KB).

Step 5: protocol sniffing (one port, three protocols)

The first 4 bytes decide: "NGA1" → RAW mode (Java clients), anything else → HTTP. An HTTP request for /ws upgrades the same socket to WebSocket. These modes are the Connection.Mode enum: SNIFF, HTTP, HTTP_DONE, WEBSOCKET, RAW.

Step 6: writing and partial writes (write() / onWritable())

We try ch.write(buf) straight away. If the OS send buffer is full, only part is written (a partial write). The rest goes into a queue and we add OP_WRITE interest. When the selector says the socket is writable we continue, and once the queue is empty we remove OP_WRITE again (otherwise the selector would wake up all the time).

Step 7: the NIO client (BotSwarm)

The load tester uses NIO on the client side too: hundreds of SocketChannels opened with non-blocking connect(), completed on OP_CONNECT with finishConnect(), all from one thread. Static files are read with a FileChannel into a ByteBuffer (Http.serveFile()).

A.3 How it is used in the game

Every player, spectator, bot, terminal client and the Control Room is a channel on this one selector. Game state lives on the selector thread only, so rooms need no locks.

A.4 Your 2-minute demo

  1. Start the server, then open the Control Room → Overview. Point at the selector circle and the "open sockets vs JVM threads" card.
  2. In a second PowerShell run ./scripts/run-bots.ps1 --bots 300. Watch the sockets climb to about 300 while threads stay about 10.
  3. Say: "Thread-per-client would need 300 threads. We use one selector thread plus 8 workers."

A.5 Likely questions

What does flip() do? And compact()?
flip() switches from writing to reading: limit = current position, position = 0. compact() copies the unread bytes to the start and sets position after them, so we can keep writing new data without losing a half-received message.
Why not use clear() instead of compact()?
clear() would throw away an incomplete frame. TCP can split a message across reads, so we must keep the partial bytes.
Why does accept() sometimes return null?
In non-blocking mode it returns immediately; null means there is no pending connection.
Why not keep OP_WRITE on all the time?
A socket is almost always writable, so the selector would wake up constantly (busy loop). We only register OP_WRITE while data is queued.
What happens if one client is slow?
Its data waits in its own queue. Nobody else is blocked. If the backlog passes 4 MB we disconnect it.
Is game state thread-safe?
Yes, by thread confinement: only the selector thread touches rooms. Workers send results back through a queue plus selector.wakeup().

Member B — TCP, HTTP, WebSocket, URLs & DNS

Lectures: TCP/IP Networking in Java (L2), Addressing, Naming and URLs (L4). Your files: server/Http.java, server/WebSocket.java, client/ConsoleClient.java, server/NetUtil.java.

B.1 The concept in simple words

TCP gives a reliable, ordered byte stream between two programs, set up with the three-way handshake (SYN, SYN-ACK, ACK) and closed with FIN. But TCP has no idea where one message ends and the next begins, so every application must define its own protocol on top. We wrote three: HTTP (to deliver web pages), WebSocket (a two-way message channel for browsers) and NGA1 (our own simple format for Java clients). URLs and DNS are how players find the server: an IP or host name, a port and a path.

B.2 How it was built

HTTP (Http.handle())

The connection collects bytes until it sees the blank line \r\n\r\n that ends HTTP headers. We split the request line (GET /path HTTP/1.1), parse headers into a map, and parse the target with java.net.URI. Then we route: / → game page, /control → Control Room page, /r/CODE → 302 redirect to /?room=CODE, /ws → WebSocket upgrade, otherwise a static file. Responses include Content-Length, security headers and Connection: close.

WebSocket upgrade and frames (WebSocket.java), written by hand from RFC 6455

// browser:  GET /ws  Upgrade: websocket  Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==
accept = Base64( SHA-1( key + "258EAFA5-E914-47DA-95CA-C5AB0DC85B11" ) )
// server:   HTTP/1.1 101 Switching Protocols   Sec-WebSocket-Accept: accept
// from now on the same TCP socket carries frames:
[FIN+opcode][MASK+length 7/16/64-bit][4-byte mask][payload XOR mask]

decode() reads the header, waits until the full frame is present, and un-masks the payload (browsers must mask, servers must not). It handles text, close, ping/pong and fragmented messages. encode() builds server frames.

NGA1 protocol (Java clients)

The client first sends the 4 bytes NGA1, then each message as [4-byte length][UTF-8 JSON]. This is the simplest correct way to mark message boundaries on a TCP stream.

The blocking client (ConsoleClient), traditional I/O for comparison

Socket s = new Socket(); s.connect(new InetSocketAddress(host, port), 4000); // 3-way handshake
out.writeInt(b.length); out.write(b);        // send one frame
int len = in.readInt(); in.readFully(buf);   // BLOCKS until the whole frame arrives

It uses three threads (socket reader, keyboard, heartbeat) because blocking calls stop a thread. It handles UnknownHostException, ConnectException, SocketTimeoutException and EOFException (server closed).

Addressing, URLs and DNS

  • LAN IP (NetUtil.lanAddresses()): lists network interfaces and keeps private IPv4s (10.x, 172.16–31.x, 192.168.x). To find the "main" one, it connects a UDP socket to 8.8.8.8 (no packet is sent) and asks which local address the OS would use.
  • Invite link: http://192.168.8.163:8080/r/K7QX (scheme, host, port, path), shown as text and as a QR code. The server answers 302 → /?room=K7QX, and the game reads room from the query string.
  • URL anatomy tool (Http.urlAnatomy()): splits any URL into scheme, user-info, host, port (default ports come from java.net.URL), path, query, fragment, and DNS levels (root / TLD / domain / subdomain). It recognises URNs like urn:isbn:….
  • DNS (Http.dnsLookup()): InetAddress.getAllByName() (forward, IPv4 and IPv6) and getCanonicalHostName() (reverse). DNS calls block, so they run on worker threads. Every new connection is reverse-resolved for the connection table (Reactor.lookupHostAsync()).

B.4 Likely questions

Why do we need our own framing if TCP is reliable?
TCP guarantees order and delivery of bytes, not message boundaries. Length prefixes (NGA1) or WebSocket headers tell the receiver where each message ends.
What is the 101 response?
"Switching Protocols": the server agrees to stop speaking HTTP on this TCP connection and start speaking WebSocket.
Why do browser frames have a mask?
The RFC requires it, to stop cache-poisoning attacks on proxies. The server XORs the payload with the 4-byte key.
URL vs URI vs URN?
A URI identifies a resource. A URL is a URI that also says where it is and how to reach it (http://…). A URN names it without a location (urn:isbn:…).
Why does the invite use an IP, not localhost?
localhost means "this device". On the phone it would point to the phone itself, so we use the laptop's LAN IP.
Why is DNS lookup done on a worker thread?
InetAddress calls block for up to seconds, and blocking the selector would freeze every player.

Member C — Multithreading: thread pool, Callable & Future

Lecture: Multithreaded Server Applications (L5). Your files: game/AiPlayer.java, Reactor.submit() / completeJobs() / execute(), server/Leaderboard.java, server/Metrics.java.

C.1 The concept in simple words

The NIO selector thread must never do slow work, because while it is busy every player freezes (remember the lecture's banking example with one slow transaction). Slow jobs are handed to a thread pool (ExecutorService). A job that returns a value is a Callable; submitting it gives back a Future, a "receipt" you use later to check isDone() and collect the result with get(). When two threads share data, access must be synchronized to avoid race conditions.

C.2 How it was built

The pool (Reactor constructor)

workers = new ThreadPoolExecutor(n, n, 30, TimeUnit.SECONDS, new LinkedBlockingQueue<>(),
        r -> new Thread(r, "arena-worker-" + counter.incrementAndGet()));   // fixed pool, named threads

n = number of CPU cores (8 on our laptop). The pool runs four kinds of job: AI moves, Diffie-Hellman maths for every new connection, DNS lookups, and saving the leaderboard to disk.

The AI as a Callable (AiPlayer implements Callable<Result>)

call() picks a move. It is not machine learning, it is search:

  • Classic 3×3: minimax with alpha-beta pruning. It tries every possible future game and picks the best move assuming perfect play (unbeatable on Legend).
  • Ultimate 9×9: Monte-Carlo Tree Search. There are too many futures, so it plays thousands of random games (65,000–85,000 in 0.6–1.6 s) and picks the move that won most often.
  • Rookie/Pro sometimes just play randomly so humans can win.

You don't need to explain the algorithm in depth. The network point is: "it is CPU-heavy, so it is a Callable on the pool."

Submitting and collecting (Reactor.submit() + completeJobs())

FutureTask<T> f = new FutureTask<T>(job) {
    protected void done() { selector.wakeup(); }   // runs AFTER the result is stored → wake the I/O thread
};
pending.add(new PendingJob<>(f, onResult, onError));
workers.execute(f);                                    // a worker thread runs AiPlayer.call()

// on the selector thread, every loop:
if (job.future.isDone()) onResult.accept(job.future.get());   // isDone() was true → get() doesn't block

Room.scheduleBot() uses this. The result callback runs on the selector thread, so it can safely change the board. If the room closes mid-search, future.cancel(true) interrupts the worker.

A real bug we fixed (good story for the viva)At first the worker called selector.wakeup() at the end of its task. But the Future is only marked "done" after the task returns, so the selector sometimes woke up, saw isDone() == false, and slept another second. Overriding FutureTask.done() fixes the race, because it runs after the result is published.

Synchronization

  • Leaderboard: the selector updates ratings, and a worker writes the file. Every method is synchronized, which prevents the lost-update race from the ticket-booking activity.
  • Metrics: counters use LongAdder (thread-safe, lock-free); logs use synchronized blocks.
  • Cross-thread hand-off: Reactor.execute() puts a Runnable on a ConcurrentLinkedQueue and calls wakeup().
  • Thread confinement: game rooms are touched only by the selector thread, so they need no locks at all.
  • ConsoleClient.send() is synchronized: two threads (keyboard and heartbeat) share one output stream and one sequence counter.

  2. In the Control Room, open Threads & AI: each move is listed as "Monte-Carlo Tree Search · 80,000 playouts · 1600 ms · arena-worker-3".

C.4 Likely questions

Runnable vs Callable?
Runnable.run() returns nothing and can't throw checked exceptions. Callable.call() returns a value and can. The AI returns a move, so it's a Callable.
Why not just create a new Thread per AI move?
Creating threads is expensive and unlimited threads exhaust resources. A fixed pool reuses 8 threads, and extra jobs wait in the queue.
What if 20 AI jobs arrive with 8 workers?
8 run and 12 wait in the LinkedBlockingQueue; no new threads are created (the lecture's 5-threads / 20-requests activity).
Why doesn't Future.get() freeze the server?
We only call it after isDone() is true, so it returns immediately.
Where is synchronization needed and where not?
Needed for data shared between threads (leaderboard, metrics, queues). Not needed for game rooms, because only one thread touches them.

Member D — UDP: finding the server on the LAN

Lecture: UDP in Java Networking. Your files: server/Discovery.java, client/LanScanner.java (also used by ConsoleClient and BotSwarm).

D.1 The concept in simple words

UDP is connectionless: no handshake, no acknowledgements, no retransmission, no ordering. You just send a datagram (header of 8 bytes: source port, destination port, length, checksum) and hope it arrives, "fire and forget". It's ideal for discovery: a client doesn't know the server's IP, so it shouts once to everybody on the network (broadcast), and the server answers. If a datagram is lost, the client simply asks again.

D.2 How it was built

Server side: a non-blocking DatagramChannel on the main selector (Discovery.onReadable())

udpChannel.bind(new InetSocketAddress(8888));             // SO_BROADCAST on, non-blocking
udpChannel.register(selector, SelectionKey.OP_READ);    // same selector as all TCP sockets
...
SocketAddress from = ch.receive(buf);                   // null = no datagram waiting (non-blocking)
if (msg.startsWith("NEONGRID_DISCOVER"))
    ch.send(ByteBuffer.wrap(beaconJson), from);         // reply straight to the sender's IP:port

The beacon is about 250 bytes of JSON: server name, TCP port, LAN IPs, host name, number of players and rooms. Unknown datagrams are ignored, and the buffer is 1500 bytes (one Ethernet MTU).

Client side: broadcast with java.net.DatagramSocket (LanScanner.scan())

  1. new DatagramSocket() (random local port) with setBroadcast(true) and setSoTimeout(200).
  2. Build target list: 255.255.255.255, each interface's directed broadcast (e.g. 192.168.8.255 from InterfaceAddress.getBroadcast()) and 127.0.0.1.
  3. Send the 20-byte query NEONGRID_DISCOVER v1 to every target, 3 times 400 ms apart (UDP may lose packets).
  4. receive() beacons for 1.5 s, de-duplicate by host, and measure the round-trip time.
  5. The terminal client then opens a normal TCP connection to the IP the beacon came from.
  → UDP query 20 bytes to 255.255.255.255:8888
  → UDP query 20 bytes to 192.168.8.255:8888
  ← beacon 247 bytes from 192.168.8.163:8888
  ✔ 192.168.8.163  tcp:8080  "NeonGrid Arena"  players=2 rooms=1  (27 ms)

Datagram length = 8-byte UDP header + 20-byte payload = 28 bytes for the query (like the lecture's length calculation activity).

Run ./scripts/run-client.ps1 with no IP and the terminal player finds the server by itself. BotSwarm does the same. The Control Room's UDP · URL · DNS tab lists every query received (sender IP:port and beacon size), and the Overview shows the UDP datagram counters.

D.5 Likely questions

Why not use TCP for discovery?
TCP needs a known IP to connect to, which is exactly what we don't have. TCP also cannot broadcast. UDP can send one datagram to every host on the subnet.
What happens if the query or beacon is lost?
UDP doesn't retransmit, so our application does: the query is sent three times and the client waits for any reply.
Why does the server reply to from?
UDP is connectionless, so each datagram carries the sender's address. We reply to that IP and port.
Is UDP secure here?
The beacon is public information only (name, port). All game traffic then goes over the secured TCP channel. Spoofing a beacon would only point a client at a server that still has to pass the DH handshake.
Why doesn't the browser use UDP discovery?
Browsers are not allowed to open raw UDP sockets. They use the URL or QR code instead, and the Java clients use UDP.

Member E — Secure network programming

Lecture: Secure Network Programming. Your files: common/Crypto.java, common/SecureLink.java, web/js/net.js, server/SecureHandshake.java, server/AdminConsole.java, Connection.onText() and TokenBucket, the Security lab in control.js.

E.1 The concept in simple words

Players connect over plain http://, often on public Wi-Fi, which is the exact threat from the lecture activity (fake Wi-Fi, eavesdropping, MITM, mark tampering 65 → 85, replayed requests, DoS). We protect the connection in layers:

  1. Agree a secret key without sending it (Diffie-Hellman).
  2. Sign every message with that key (HMAC-SHA256), so changes and forgeries are detected.
  3. Number every message, so old messages can't be replayed.
  4. Limit the message rate and drop idle sockets (DoS protection).
  5. Check everything on the server: authentication, authorization and game rules.

E.2 How it was built

1. Diffie-Hellman key agreement (Crypto.java and net.js)

p = 2048-bit safe prime (RFC 3526 group 14),  g = 2
browser:  a = random 256-bit,  A = g^a mod p   → sends A in "hello"
server:   b = random 256-bit,  B = g^b mod p   → sends B in "welcome"   (computed on a worker thread)
both:     s = B^a mod p = A^b mod p = g^ab mod p     K = SHA-256(hex(s))
// an eavesdropper sees A and B but cannot compute g^ab (discrete logarithm problem)

2. The signed envelope (SecureLink.seal() / open())

frame = HMAC_SHA256(K, json) as 64 hex chars  +  json
        3f1c…a9e0{"t":"move","cell":40,"seq":7}
open(): recompute the HMAC → mismatch?  → TAMPER   (changed in transit, or forged without K)
        seq ≤ last accepted seq?        → REPLAY   (old message sent again)

MACs are compared with MessageDigest.isEqual (constant time), so timing can't leak the MAC. The browser has no crypto.subtle on plain http, so net.js contains our own SHA-256 and HMAC, and uses BigInt for DH.

3. Authentication

  • Players: the server gives each session a random 256-bit token, sent encrypted (XOR with SHA-256(K‖"token")). After a refresh or Wi-Fi drop, the browser proves ownership with HMAC(token, newDhPublicKey). The token itself never travels, and the proof can't be reused.
  • Admin (Control Room): challenge-response. Each connection gets a random nonce, and the browser sends HMAC(SHA-256(password), nonce). The server computes the same value and compares (AdminConsole.login()). The password never crosses the network, a captured proof is useless on another connection, and 5 failures close the connection.

4. Authorization and server-authoritative rules

Admin-only commands (stats, dns, url) return FORBIDDEN without login. In Room.move() the server checks: is there a game, is the sender a player (not a spectator), is it their turn, is the cell legal (Board.whyIllegal())? A hacked browser can't cheat because the client only sends "I want cell N".

5. DoS protection and best practices

  • Token bucket (Connection.TokenBucket): 40-message burst, refilled at 20 per second, checked before any expensive work. Excess messages are dropped (RATE_LIMIT), and 400 violations in 10 s disconnects the client.
  • Frame limit 64 KB, output backlog limit 4 MB, idle and slowloris timeouts (10 s before handshake, 45 s after), connection cap.
  • Input validation (names, chat, JSON depth, DH hex), path-traversal block (/..%2f… → 403), HTML escaping in the UI, security headers, no secrets or stack traces in errors.

E.5 Likely questions

Is the data encrypted?
No. Messages are signed, not encrypted: we provide integrity, authenticity and replay protection, not confidentiality. In production we would run the same protocol inside TLS (wss://) with a CA certificate. Being honest about this earns marks.
Can a MITM break Diffie-Hellman?
A passive eavesdropper cannot. An active attacker who intercepts both sides could run two separate handshakes. Certificates (TLS) solve that by authenticating the server.
Why HMAC and not plain SHA-256?
Anyone can recompute a plain hash after changing the data. HMAC needs the secret key, so only the two real parties can produce a valid MAC.
Why does seq stop replays?
The server remembers the last accepted seq. A copied old frame has a smaller or equal seq and is rejected, even though its MAC is valid.
Why not send the admin password directly?
It would be visible to anyone sniffing the Wi-Fi. With challenge-response the server proves you know it without it ever being transmitted.
Make it yoursChange the rate limit in Connection.java (new TokenBucket(40, 20)) to (10, 5), rebuild, and show that the flood now drops more messages. Or change the admin lock-out from 5 to 3 attempts in AdminConsole.login().
